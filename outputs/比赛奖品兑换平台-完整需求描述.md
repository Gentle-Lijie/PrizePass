## 1. 需求概述

建设一个“比赛奖励兑换平台”。管理员创建比赛、配置奖品和兑换规则，导入获奖人名单，并为获奖人分配不同额度的唯一兑换码。平台可以根据可编辑的邮件模板，通过 SMTP 自动向获奖人发送兑换码通知。兑换人无需注册、登录或创建平台账号，只需输入兑换码，在额度范围内选择奖品，填写自提所需的姓名、手机号等个人信息并提交兑换申请。平台使用管理员录入的自有库存完成备货和自提核销，管理员通过 Webhook、SMTP 邮件等通知渠道接收关键业务通知。

平台应支持管理员直接维护奖品，也应支持粘贴京东商品链接后自动提取商品标题、图片、描述、规格和参考价格等资料；京东仅作为商品资料抓取来源，不是采购方、供应商或库存来源。抓取结果必须先经过管理员预览和确认，不能未经确认直接上线。

### 1.1 要解决的问题

- 比赛奖品、获奖人名单、不同额度兑换码、库存和兑换状态分散在表格或人工沟通中。
- 兑换码容易重复、泄露、被重复使用或无法追踪。
- 奖品价格、库存、图片和描述维护成本高。
- 获奖人名单导入、兑换码分配和发码通知需要人工处理，容易错发、漏发或重复发送。
- 兑换提交后无法及时通知运营或业务系统。
- 缺少完整的兑换订单、自提核销、异常、审计和通知发送记录。

### 1.2 产品目标

1. 管理员可以在一个后台完成比赛、奖品、获奖人、兑换码批次和库存的配置。
2. 兑换人可以无需账号，简单、安全地完成“输入兑换码—选奖品—填写自提信息—提交兑换”。
3. 每个兑换码只能按规则使用，额度、有效期、订单和状态可追踪。
4. 奖品信息可以人工维护，也可以通过商品链接辅助录入。
5. 管理员可以导入获奖人、按批次分配兑换码，并自动发送可编辑模板的兑换码邮件。
6. 兑换、审核、自提备货、现场核销和异常均能通过后台和通知渠道闭环管理。

### 1.3 第一版不包含的内容

以下能力不作为第一版的默认范围，除非业务确认后单独立项：

- 任何采购、供应商结算、京东下单、京东支付和京东订单同步。
- 平台作为完整电商系统处理支付、退款、售后和发票。
- 兑换人注册、登录、个人账户、积分、余额或用户中心。
- 兑换人用现金补差价、兑换现金或兑换余额提现。
- 一个兑换码拆分成多次兑换多个奖品。
- 对京东页面进行登录绕过、验证码绕过、反爬绕过或其他不合规抓取。
- 京东价格/库存的自动同步，以及将京东页面信息直接当作可兑换库存。

第一版定位为“奖励额度与自有库存奖品兑换管理平台”。京东链接抓取只用于辅助创建奖品；平台不在京东采购、不付款、不同步京东库存，也不把京东页面价格当作实际结算依据。管理员负责维护平台真实库存，并从该库存备货、安排自提和完成现场核销。

平台需要保存获奖人的业务联系人资料，用于分配兑换码和发送通知，但这不等于建立用户账号。获奖人无需登录，也不能通过获奖人资料进入平台；兑换流程仍由兑换码触发。

### 1.4 已确认的业务边界

- 奖品来自业务方提供或持有的自有库存，平台只管理数量、预占、出库和兑换状态。
- 不需要采购模块，不需要供应商结算，不需要京东订单或支付对接。
- 京东链接的价值在于快速获取商品是什么、长什么样、图片、描述和规格等资料。
- 同一比赛可以配置多个兑换码批次，每个批次有自己的额度和数量，例如 300 元码 100 个、500 元码 20 个。
- 管理员可以导入获奖人名单，并将获奖人分配到指定兑换码批次；分配后系统自动发送兑换码邮件。
- 平台兑换额度、平台库存、可兑换状态和自提状态均以后台管理员配置为准。
- 奖品交付方式固定为自提，不支持收货地址、快递配送或物流履约。
- 兑换申请至少要求填写兑换人姓名和手机号；邮箱、证件信息等字段按业务需要配置。
- 获奖人邮箱是自动发送兑换码邮件的必要字段；没有邮箱的导入记录必须进入异常报告，不得静默跳过。

## 2. 核心概念与推荐的第一版规则

| 概念 | 定义 |
|---|---|
| 比赛（Event） | 一次独立的比赛或奖励活动，包含奖品范围、兑换规则、自提地点和兑换码批次。 |
| 获奖人（Winner/Recipient） | 被导入比赛名单、需要接收兑换码通知的人；是业务联系人记录，不是平台用户账号。 |
| 兑换码批次（Code Batch） | 同一比赛下的一组相同额度、有效期和数量的兑换码。 |
| 兑换码（Code） | 与比赛、兑换码批次、兑换额度和可选获奖人记录绑定的唯一凭证；不要求获奖人拥有平台账号。 |
| 奖品（Reward） | 可被兑换的实物、电子券、服务或其他奖励。 |
| 兑换订单（Redemption Order） | 兑换人使用兑换码选择奖品并提交自提信息后产生的业务记录。 |
| 自提履约（Pickup Fulfillment） | 管理员备货、通知领取、现场核验并完成奖品交付的过程；不包含配送和采购。 |

### 2.1 推荐的 MVP 默认规则

1. 一个比赛可以有多个兑换码批次，每个批次可设置不同额度、数量和有效期；例如同一比赛同时存在 100 元、300 元和 500 元兑换码。
2. 管理员可导入获奖人，并将其分配到指定兑换码批次；每名获奖人默认获得一个兑换码，是否允许一个人获得多个码由比赛配置决定。
3. 一个兑换码默认只能兑换一个奖品；兑换码不绑定平台用户账号，也不要求兑换人注册或登录。
4. 每个兑换码有独立的“兑换码额度”，兑换时以该额度判断是否符合兑换资格；该字段与京东抓取的参考价格完全分开保存。
5. 奖品兑换额度必须小于或等于兑换码额度；第一版不允许补差价。
6. 兑换额度低于兑换码额度时，剩余额度不返现、不结转、不自动生成新码。
7. 兑换码有效期由兑换码批次配置，也可在单个兑换码上覆盖；过期后不可提交兑换。
8. 兑换人提交后，兑换码进入“锁定/待处理”状态，防止重复提交；订单被拒绝或取消时，按规则恢复兑换码或由管理员手工补发。
9. 奖品价格、名称、描述和图片在订单提交时生成快照，之后管理员修改奖品不影响历史订单。
10. 京东链接导入的标题、图片、描述、规格和价格都是候选资料；平台真实库存、兑换额度和是否可兑换以管理员确认的配置为准，京东库存不参与判断。
11. 奖品仅支持自提；兑换申请至少需要姓名和手机号，不收集收货地址、邮编或快递信息。可选收集邮箱、证件信息和备注。
12. 获奖人导入确认后，系统自动向有效邮箱发送兑换码邮件；同一条获奖人记录不得因重试或重复导入而重复发码，除非管理员明确执行重发。

如果业务希望“300 元兑换码可以多次消费，直到余额用完”，应将其作为独立规则设计，而不是在单次兑换码模型上临时扩展。

## 3. 后台角色与权限

### 3.1 角色

| 角色 | 主要能力 |
|---|---|
| 系统管理员 | 管理后台账号、角色、系统配置、全部比赛和审计日志。 |
| 比赛管理员 | 创建和维护自己负责的比赛、奖品、库存、获奖人名单和兑换码批次。 |
| 自提运营人员 | 查看兑换订单、准备奖品、确认到场信息、完成自提核销和更新状态。 |
| 兑换页面访问者 | 无平台账号；输入兑换码、浏览可兑换奖品并提交自提信息。 |
| 外部系统 | 通过 Webhook 接收平台事件；默认只接收，不直接修改平台数据。 |

### 3.2 权限原则

- 比赛管理员默认只能访问被授权的比赛。
- 兑换人姓名、手机号、邮箱、证件信息和兑换码原文等敏感信息按最小权限展示。
- 获奖人邮箱、手机号、兑换码分配关系和邮件发送记录按最小权限展示。
- 删除采用“归档/停用”，不允许直接物理删除有订单或审计记录的数据。
- 所有影响额度、兑换码、订单状态、库存和自提核销状态的操作必须记录操作人、时间、前后值和原因。

平台不建立兑换人账号、密码、登录会话、个人资料或用户中心。后台账号是独立的管理员体系；兑换人只通过兑换码进入一次性兑换流程。

## 4. 主要业务流程

### 4.1 管理员配置比赛

1. 创建比赛，填写名称、说明、活动时间和兑换截止时间。
2. 配置兑换规则：兑换截止时间、自提地点、自提时间、必填个人信息字段和是否需要人工审核。
3. 选择或创建本比赛可兑换的奖品。
4. 通过人工录入、Excel/CSV 导入或京东链接导入维护奖品。
5. 创建一个或多个兑换码批次，为每个批次设置额度、数量和有效期。
6. 导入获奖人名单，在导入预览中为每行选择兑换码批次或兑换额度。
7. 确认导入后，系统按规则生成/分配兑换码，并自动使用邮件模板向获奖人发送兑换码。
8. 配置 Webhook、SMTP 邮件、邮件模板和通知事件，预览并测试发送。
9. 预览全部配置，确认后发布比赛。

### 4.2 获奖人导入、兑换码分配与自动发码

1. 管理员下载比赛专用导入模板，填写获奖人姓名、邮箱、手机号、外部获奖人 ID，以及对应的兑换码批次或兑换额度。
2. 系统执行格式校验、必填字段校验、重复记录校验、批次额度校验和批次可用码数量校验。
3. 管理员查看导入预览和逐行错误报告；预览阶段不生成兑换码、不发送邮件。
4. 管理员确认导入后，系统创建或更新获奖人记录，并为每名获奖人默认分配一个兑换码；如配置允许，可按导入字段分配多个兑换码。
5. 如果批次中没有足够的可分配兑换码，相关记录进入“待分配/失败”状态，不得静默发送错误额度的兑换码。
6. 兑换码分配成功后，若比赛和获奖人记录均开启通知，系统异步发送兑换码邮件；邮件发送失败不撤销兑换码，但进入失败队列并提示管理员重试。
7. 重复导入同一个外部获奖人 ID时，系统不得重复生成兑换码或重复发送邮件，除非管理员明确选择“重新发码”。
8. 管理员可以查看每个获奖人的兑换码分配关系、邮件发送状态、失败原因和重发记录。

### 4.3 兑换人提交兑换申请

1. 兑换人打开比赛兑换页，输入兑换码；不注册、不登录、不创建账号。
2. 系统校验兑换码格式、比赛状态、有效期、使用状态和剩余额度。
3. 根据兑换额度筛选可兑换奖品，并展示名称、描述、图片、兑换额度和可用状态。
4. 兑换人查看奖品详情，选择奖品及必要规格。
5. 兑换人填写自提信息：姓名和手机号为必填；邮箱、证件信息、备注等按比赛配置。
6. 系统展示确认页，明确奖品、兑换额度、自提地点、自提时间、个人信息和不可撤销规则。
7. 兑换人提交后，系统原子化创建订单并锁定兑换码，防止重复提交。
8. 系统按配置向后台收件人、Webhook 和兑换人邮箱（如填写）发送通知。

### 4.4 管理员处理订单

1. 运营人员在后台查看待审核或待自提订单。
2. 确认平台自有库存可供应后批准订单；如库存不足或无法履约，填写原因并拒绝订单。
3. 从自有库存备货，设置订单为“待自提”，并通知兑换人自提地点、时间和注意事项。
4. 兑换人到指定地点自提；运营人员核验订单号/兑换码及手机号等信息。
5. 运营人员登记自提时间和核销人员，将订单标记为“已自提/已完成”。
6. 系统按配置通知后台收件人和兑换人邮箱（如填写），并保留完整状态变化记录。

## 5. 功能需求

### 5.1 比赛管理

**FR-EVT-001 创建和编辑比赛**

比赛至少包含以下字段：

- 比赛名称
- 比赛编码（系统生成且唯一）
- 比赛简介、规则说明和客服联系方式
- 比赛封面图（可选）
- 比赛开始时间、结束时间
- 兑换开始时间、兑换截止时间
- 比赛状态：草稿、未开始、进行中、兑换中、已结束、已归档
- 兑换码批次规则（每个批次的额度、数量、有效期和备注）
- 本比赛可用的奖品列表
- 自提地点、地址、开放时间和领取说明
- 自提申请必填字段：默认包含姓名、手机号
- 可选字段：邮箱、证件信息、备注
- 是否允许管理员手工审核兑换
- 自动发送兑换码邮件：开启/关闭
- 默认兑换码邮件模板及比赛级模板覆盖
- 通知配置

要求：

- 草稿状态可以编辑；发布前必须完成必要字段校验。
- 已产生订单的比赛不能直接修改影响历史订单的规则；修改应形成新版本或只影响未使用兑换码。
- 比赛结束后，可配置为继续允许已分配/已发送兑换码兑换至兑换截止时间。
- 比赛支持复制，复制时不复制历史兑换码和订单。

**FR-EVT-002 比赛状态控制**

- 只有符合时间和状态条件的比赛允许新兑换；获奖人导入和兑换码发放仍由后台权限控制。
- 管理员可手工暂停兑换，暂停时已提交订单不受影响。
- 归档后前台不可见，但历史订单、代码和审计记录仍可查询。

### 5.2 奖品管理

**FR-RWD-001 奖品字段**

奖品至少支持以下字段：

| 字段 | 说明 |
|---|---|
| 奖品 ID/SKU | 平台内部唯一标识。 |
| 名称 | 前台展示名称。 |
| 简短描述 | 列表页展示。 |
| 详细描述 | 详情页展示，支持富文本或 Markdown 的受限子集。 |
| 图片 | 支持上传或图片 URL；至少一张主图，可选多张详情图。 |
| 平台兑换额度 | 兑换人实际消耗的额度，使用人民币分存储。 |
| 参考市场价 | 可选，仅用于展示或运营参考，不参与资格判断。 |
| 资料来源 | 京东链接、人工录入或其他资料来源；仅用于记录商品资料来源。 |
| 来源链接 | 外部商品链接。 |
| 规格/变体 | 颜色、型号、容量等可选项。 |
| 库存模式 | 有限自有库存、无需库存的电子奖励、待确认。 |
| 库存数量 | 由管理员录入或批量导入的平台真实库存。 |
| 已预占数量 | 已被待处理订单锁定、尚未完成自提核销的数量。 |
| 库存批次/有效期 | 可选，用于有批次、序列号或有效期的奖品。 |
| 自提说明 | 自提地点、开放时间、领取要求和注意事项。 |
| 奖品类型 | 实物、电子券、服务、其他。 |
| 状态 | 草稿、上架、售罄、下架、归档。 |
| 排序权重 | 控制前台展示顺序。 |
| 更新时间 | 用于审计和资料更新判断。 |

要求：

- 管理员可新增、编辑、复制、上下架、归档和批量导入奖品。
- 奖品必须支持人工修改抓取结果。
- 兑换额度必须为大于 0 的金额；不能使用浮点数直接计算金额。
- 奖品下架后不能产生新订单，已产生订单不受影响。
- 任何已产生订单的奖品信息必须保留订单快照。
- 如果奖品有规格，必须在订单中保存兑换人最终选择的规格。

**FR-RWD-002 京东链接导入**

管理员输入一个商品链接后，系统执行以下流程：

1. 检查链接格式和允许的来源域名。
2. 请求商品公开页面或使用已获授权的接口获取信息。
3. 尝试提取商品标题、主图、详情图、描述、参考价格、规格、商品 ID 和来源链接；如果页面存在库存提示，只作为附加参考，不写入平台可用库存。
4. 展示导入预览页，标出成功、缺失和不确定的字段。
5. 管理员可以修改字段、选择主图、设置平台兑换额度和库存。
6. 管理员点击“确认保存”后，才创建或更新平台奖品。

异常处理：

- 页面无法访问、登录限制、验证码、动态渲染或字段解析失败时，应显示清晰错误，并允许管理员改为手工录入。
- 抓取任务设置超时、重试和失败日志；失败不能阻塞其他后台功能。
- 不实施绕过验证码、访问控制或反爬机制的行为。
- 抓取结果保存来源链接、抓取时间和解析版本，便于追溯。
- 上线前应由业务/法务确认对外部页面内容、图片和描述的使用符合适用的平台规则及授权要求。
- 京东页面上的价格、库存和促销信息不作为平台库存或兑换资格依据；平台只保存管理员确认后的资料和自有库存。

**FR-RWD-003 自有库存管理**

平台库存是唯一的可兑换库存来源，必须由管理员维护，不从京东或其他外部页面自动推断。

- 支持首次录入、批量导入、增加、减少、盘点调整和批量下架。
- 支持按奖品 SKU、规格、库存批次或序列号管理库存；是否需要批次/序列号由奖品类型决定。
- 展示总库存、已预占库存、已出库库存和可用库存。
- 每次库存调整必须填写数量、原因、操作人和时间，并形成库存流水。
- 兑换订单提交时预占可用库存；订单被拒绝或取消时释放预占库存；订单自提核销时扣减实际库存。
- 可用库存为 0 时自动标记为售罄或隐藏，具体行为由比赛/奖品配置决定。
- 支持 CSV/XLSX 导入自有库存，导入前必须预览并校验 SKU、规格和数量。
- 不提供外部采购、供应商库存、京东库存同步或自动补货功能。

### 5.3 获奖人、兑换码批次和兑换码管理

**FR-COD-001 获奖人导入与管理**

获奖人是用于兑换码分配和邮件通知的业务联系人记录，不是平台用户账号。平台支持：

- 单个新增、编辑、停用和查看获奖人。
- 通过 CSV/XLSX 导入获奖人名单，导入前预览，导入后提供逐行错误报告。
- 通过外部系统 API 或文件导入获奖人名单；接口导入也必须支持幂等。
- 记录获奖人姓名、邮箱、手机号、外部获奖人 ID、内部备注和导入来源。
- 为获奖人选择兑换码批次，或从导入字段读取兑换码批次标识/兑换额度。
- 查看获奖人的兑换码分配、当前兑换码状态、邮件发送状态和重发记录。

推荐导入字段：

```text
external_winner_id, name, email, mobile, code_batch_key,
entitlement_amount, code_quantity, notification_enabled, note
```

导入规则：

- `name`、`email` 和 `code_batch_key`/`entitlement_amount` 为默认必填字段；`external_winner_id` 推荐必填，用于重复导入幂等。
- 邮箱必须通过格式校验；缺失或格式不正确的邮箱不得进入自动发码队列。
- 当同一比赛中存在多个额度批次时，每行必须明确指定批次或额度；系统不得猜测应分配的额度。
- 外部获奖人 ID 在同一比赛内唯一；没有外部 ID 时，系统以邮箱作为辅助去重键并给出重复警告。
- 导入预览阶段不生成兑换码、不分配兑换码、不发送邮件；管理员确认后才执行后续动作。
- 导入失败、批次额度不匹配、可用码不足或邮箱无效的记录进入错误报告，不影响其他有效行，但不得静默跳过。

**FR-COD-002 兑换码批次**

同一比赛下可以创建多个兑换码批次。每个批次至少包含：

- 批次名称或内部备注
- 兑换额度，例如 100 元、300 元、500 元
- 计划生成数量
- 生效时间和过期时间
- 批次状态：草稿、已生成、已分配、已发码、暂停、完成、作废
- 已生成、已分配、已发邮件、已使用、已过期、已作废数量统计

要求：

- 管理员可以在同一比赛中创建不同额度的多个批次。
- 支持批量生成，例如“300 元 × 100 个”和“500 元 × 20 个”。
- 兑换码生成后，额度应固化在兑换码上；只有未分配且未使用的码允许在有审计记录的情况下调整。
- 批次需要展示可用码数量；可用码不足以满足已确认的获奖人导入时，系统应阻止相关分配并提示管理员。
- 批次复制时只复制额度和规则，不复制已有兑换码和兑换记录。

**FR-COD-003 兑换码生成、分配与自动发放**

- 支持预生成兑换码池，也支持在获奖人导入确认时按需生成兑换码。
- 支持按比赛和兑换码批次批量生成兑换码。
- 支持将一个批次中的可用兑换码按导入顺序或指定规则分配给获奖人。
- 每名获奖人默认分配一个兑换码；只有比赛开启“允许多码”并且导入数据指定 `code_quantity` 时，才允许分配多个兑换码。
- 兑换码分配必须记录获奖人、批次、分配时间、分配操作来源和操作人/系统任务。
- 分配成功后，系统自动创建“兑换码通知”邮件任务；通知默认包含兑换码原文、兑换额度、有效期、兑换入口和比赛说明。
- 当比赛关闭自动发码时，分配成功后只创建待发送任务，由管理员在后台批量确认发送；MVP 默认开启自动发码。
- 邮件任务异步执行；发送成功记录邮件时间和模板版本，发送失败记录失败原因并进入可重试队列。
- 邮件失败不自动作废兑换码；管理员可以重新发送给当前获奖人，也可以先更换邮箱后再发送。
- 支持单个重发、批量重发和只重发失败邮件；重发必须记录操作人、时间、原因和使用的模板版本。
- 对同一获奖人、同一兑换码和同一模板版本，系统应使用幂等键避免后台任务重复发送；管理员主动点击重发时可生成新的发送记录。
- 只有管理员明确执行“解绑/换码/重发新码”时，才允许改变获奖人和兑换码的分配关系。
- 兑换码必须使用不可预测的随机值，不能只使用递增数字或可推断信息。
- 兑换码在全平台范围内唯一，至少支持大小写不敏感校验和易混淆字符规避。
- 兑换码可以携带展示前缀，但前缀不能作为安全凭证。
- 管理员导出原始兑换码时必须二次确认并记录审计日志；下载文件应设置有效期或由管理员自行安全保存。
- 系统不在普通日志、Webhook 或错误信息中记录完整兑换码，兑换码邮件是经过授权的例外场景。

**FR-COD-004 兑换码作废、补发与状态**

- 支持单个或批量作废、重新生成和导出兑换码。
- 作废、补发和换码必须保留原兑换码与新兑换码的关联关系。
- 兑换码批次、获奖人分配和发码邮件都支持审计追踪。
- 支持在获奖人导入完成、兑换码分配、邮件发送成功/失败、兑换码导出、过期和作废时触发通知事件。

**FR-COD-005 兑换码状态**

建议状态：

- `generated`：已生成，未分配
- `assigned`：已分配给获奖人，等待发码邮件
- `issued`：已发送邮件或已导出，可兑换
- `locked`：已提交订单，正在审核或自提处理
- `redeemed`：已完成自提核销
- `expired`：已过期
- `revoked`：已作废
- `reissued`：已被新码替代

状态变化必须符合状态机，禁止通过普通编辑直接篡改状态。

**FR-COD-006 兑换码安全校验**

- 输入错误时只返回“兑换码无效或不可用”，不能泄露是不存在、已使用还是属于其他比赛。
- 对 IP、设备和兑换码实施尝试次数限制；平台不建立兑换人账号。
- 连续失败触发短暂锁定和后台告警。
- 兑换页面可以校验手机号格式，但默认不要求短信验证码或账号登录；如未来需要验证码，应作为独立能力增加。
- 兑换码不能出现在 URL、前端明文日志或第三方通知正文中，除非业务明确配置且接受风险。

### 5.4 前台奖品浏览与兑换

**FR-RED-001 兑换码验证页**

- 输入兑换码后显示比赛名称、有效期、可用额度和兑换说明。
- 不向前台展示获奖人名单或预置个人信息；获奖人资料只在后台用于兑换码分配和邮件通知。
- 无效、过期、已使用、被作废或比赛暂停时，给出统一但可理解的提示。

**FR-RED-002 奖品列表和详情**

- 仅展示当前比赛关联、已上架且符合兑换规则的奖品。
- 默认只展示兑换额度不超过兑换码可用额度的奖品。
- 支持按奖品类型、额度、库存状态筛选和关键词搜索。
- 详情页展示图片、名称、描述、规格、平台兑换额度、自提说明和注意事项。
- 对外部商品价格标注“参考信息”，不要使用户误以为平台承诺外部平台实时价格。

**FR-RED-003 提交兑换订单**

- 提交前展示最终确认页。
- 所有奖品均仅支持自提。
- 姓名和手机号为必填；邮箱、证件信息、备注等字段按比赛配置。
- 不提供收货地址、邮编、快递公司或物流单号字段。
- 提交接口必须支持幂等，兑换人重复点击不能生成多个订单。
- 系统在同一事务或等价可靠机制中完成：校验兑换码、校验奖品、锁定库存、创建订单、锁定兑换码。
- 提交成功后显示订单号、订单状态、自提地点、自提时间和领取注意事项。
- 订单创建后不允许兑换人自行更换奖品；是否允许后台修改由权限和审计规则控制。

### 5.5 订单和履约管理

**FR-ORD-001 订单字段**

- 订单号、比赛、兑换码和兑换码批次引用
- 奖品及规格快照
- 兑换额度快照、参考价格快照
- 自提联系人信息快照：姓名、手机号；以及按配置收集的邮箱、证件信息、备注
- 自提地点和自提规则快照
- 订单状态、状态变更时间和原因
- 审核人、审核时间
- 内部备货/核销批次号（可选）
- 自提时间、核销人员和核销备注
- 备注、附件和审计记录

**FR-ORD-002 订单状态**

建议状态：

```text
submitted       已提交，待审核
approved        已审核，待备货
rejected        已拒绝
ready_for_pickup 已备货，待自提
picked_up       已自提并核销
completed       已完成
cancelled       已取消
```

要求：

- 后台可按比赛、状态、日期、奖品、兑换码、手机号后四位和订单号筛选。
- 支持批量审核、导出自提备货清单和批量更新自提状态，但批量操作必须有预览和审计。
- 拒绝、取消必须填写原因。
- 订单状态变化自动触发通知和 Webhook（按配置执行）。
- 订单详情显示兑换码脱敏值，只有具备权限的管理员才能查看完整关联信息。
- 自提核销必须由有权限的运营人员执行，并记录核销时间、核销人员和核验结果。

**FR-ORD-003 库存处理**

- 有限库存奖品在提交时进行库存预占。
- 订单拒绝或取消时按配置释放预占库存；完成自提核销时扣减实际可用库存。
- 库存不足时禁止创建新订单，并提示管理员补充库存或下架奖品。
- 平台库存由管理员录入和调整，是唯一的可兑换库存来源；京东页面库存不参与判断。
- 预占必须有超时释放策略，例如订单长时间未审核时自动提醒或释放；具体时长由业务配置。

**FR-ORD-004 自提配置与核销**

- 比赛必须至少配置一个自提地点；支持多个自提地点时，兑换人可在提交时选择一个可用地点。
- 自提地点至少包含名称、地址、开放时间、现场联系人/联系电话和领取说明。
- 兑换申请不出现收货地址、配送方式、物流公司、物流单号或配送费用字段。
- 兑换人提交姓名和手机号；后台可按比赛配置邮箱、证件信息、备注等附加字段。
- 订单审核通过后进入“待备货”，运营人员确认奖品准备完成后进入“待自提”。
- 现场核销时，运营人员至少核验订单号或兑换码，以及兑换人手机号；可按业务要求增加姓名或证件核验。
- 核销成功后记录自提时间、核销人员和核验备注，并将库存从预占转为已出库。
- 已核销订单不可重复核销；重复核销尝试必须被拒绝并记录日志。
- 可选生成自提二维码或短核销码，但其作用仅限于现场核销，不构成用户账号。

### 5.6 通知中心

**FR-NOT-001 通知渠道**

第一版必须支持抽象的通知适配器，并至少实现以下渠道：

- Email：SMTP。管理员可配置 SMTP Host、Port、TLS/STARTTLS、用户名、密码/密钥、发件人、回复地址、收件人和模板。
- Webhook：向业务系统配置的 HTTPS 地址发送 JSON 事件，支持签名、重试和幂等。
- 管理员后台通知：站内待处理计数和失败提示。

后续可增加短信、企业微信、钉钉、Slack 或其他 HTTP/邮件适配器，不改变业务事件模型。

**FR-NOT-002 触发事件**

至少支持以下事件：

- 获奖人导入完成/导入失败
- 兑换码已分配给获奖人
- 兑换码邮件发送成功/失败/重发
- 兑换码批次已生成/已导出/已作废
- 兑换码即将过期
- 兑换订单已提交
- 订单已批准
- 订单被拒绝或取消
- 订单已备货待自提
- 订单已自提核销/已完成
- 奖品库存不足
- 京东链接导入失败
- Webhook 或 SMTP 连续发送失败

管理员可以按比赛、事件类型和渠道配置通知目标、启用状态、模板、是否自动发送以及敏感字段范围。

同一个业务事件可以同时发送到多个渠道。例如“兑换码已分配”可以同时触发获奖人兑换码邮件、运营邮箱和业务 Webhook；任何一个渠道失败，都不能影响其他渠道，且每个渠道独立记录发送结果。

**FR-NOT-002A SMTP 邮件配置**

- 支持全局 SMTP 配置，也支持按比赛覆盖发件人、收件人和模板。
- 密码或应用专用密钥必须加密存储，后台只显示脱敏值。
- 支持发送测试邮件，测试结果要记录在通知日志中。
- 兑换码通知邮件的收件人默认取获奖人记录中的 `email`；运营告警、导入结果和订单通知的收件人由比赛/系统通知配置决定。
- 不允许在模板正文中手工写入另一个获奖人的地址；收件人必须由系统根据业务对象解析，并在发送前记录脱敏目标。
- 支持纯文本和 HTML 邮件模板；模板变量至少包括获奖人姓名、比赛名称、兑换码、兑换额度、有效期、兑换入口、自提地点、自提时间、订单号、奖品名称和订单状态。
- SMTP 连接超时、认证失败、TLS 失败和收件人拒绝必须记录明确错误，并支持重试。

**FR-NOT-002B 邮件模板编辑**

- 支持创建、编辑、复制、预览、启用、停用和版本化邮件模板。
- 模板类型至少包括：兑换码通知、兑换码重发、订单已提交、订单已批准/待备货、订单待自提、订单已自提、订单被拒绝或取消、通知失败告警。
- 模板支持邮件主题、纯文本正文、HTML 正文、发件人显示名、回复地址和附件开关等字段。
- 管理员可以为全局模板设置默认版本，并在比赛级别覆盖模板；比赛模板优先于全局模板。
- 模板编辑器应提供可用变量列表、变量插入、变量校验、示例数据预览和发送测试邮件。
- 未知变量、必填变量缺失或模板语法错误时不能发布模板；系统应指出具体错误位置。
- HTML 模板需要进行安全清理，禁止脚本、外部危险资源和未授权的动态代码执行。
- 模板发布后保留历史版本；历史邮件必须关联发送时使用的模板版本，后续模板修改不能改变已发送记录。
- 兑换码通知模板必须明确展示兑换码、兑换额度、有效期、兑换入口和比赛规则；是否展示完整兑换码只能通过模板权限和审计控制。

兑换码邮件推荐变量：

```text
{{winner_name}}, {{winner_email}}, {{event_name}}, {{event_description}},
{{redemption_code}}, {{entitlement_amount}}, {{code_expires_at}},
{{redemption_url}}, {{pickup_location}}, {{pickup_hours}}, {{support_contact}}
```

**FR-NOT-003 Webhook 要求**

- 使用 HTTPS；支持签名密钥。
- 每个事件带有 `event_id`、`event_type`、`occurred_at`、`event_version` 和业务对象 ID。
- 请求头建议包含 `X-Webhook-Event-Id`、`X-Webhook-Timestamp`、`X-Webhook-Signature`。
- 签名建议基于原始请求体、时间戳和共享密钥生成，具体算法由技术方案确定。
- 发送失败应自动重试，并记录每次响应状态、响应摘要和下次重试时间。
- 接收方必须能够根据 event_id 幂等处理。
- 后台支持手工重试单条失败事件和发送测试事件。
- 默认不发送完整兑换码、完整手机号和证件信息；敏感字段只在业务明确需要时按权限和配置发送。系统不发送收货地址，因为平台不支持配送。

示例事件：

```json
{
  "event_id": "evt_01H...",
  "event_type": "redemption.submitted",
  "event_version": "1",
  "occurred_at": "2026-08-12T10:30:00+08:00",
  "data": {
    "order_id": "ord_01H...",
    "event_id": "event_01H...",
    "reward_id": "reward_01H...",
    "entitlement_amount": 30000,
    "currency": "CNY",
    "status": "submitted"
  }
}
```

### 5.8 审计、客服和异常处理

- 记录比赛配置、奖品信息、兑换码、订单和通知配置的新增、修改、停用、审批、重试等操作。
- 记录操作前后值，敏感字段脱敏或加密。
- 后台支持按订单号、兑换码后四位、兑换人手机号后四位和内部备货/核销批次号检索。
- 支持客服为订单添加内部备注，不直接修改原始订单事实。
- 对常见异常提供明确处理路径：奖品售罄、库存盘点差异、自提信息错误、重复提交、订单拒绝、通知失败、抓取失败。

## 6. 核心业务规则

### 6.1 额度和金额

- 所有金额以人民币分为最小单位存储，例如 300 元保存为 `30000`。
- `兑换码额度`决定兑换人的资格上限；`奖品平台兑换额度`决定该奖品消耗多少额度。
- 参考市场价、外部页面价格不能自动覆盖平台兑换额度。
- 一张兑换码只能兑换一个奖品时，订单成功后不产生找零或余额。
- 任何额度调整必须记录操作人、原因和生效范围。

### 6.2 有效期

- 兑换码在 `issued` 且当前时间未超过有效期时可使用。
- 订单提交时锁定有效资格；提交后即使兑换截止时间到达，也按照订单状态继续处理。
- 过期前可发送提醒，提醒时间可配置。
- 已过期的码不能通过普通编辑恢复，恢复必须走带原因的管理员操作。

### 6.3 取消、拒绝和恢复

推荐规则：

- 待审核订单被拒绝：兑换码恢复为 `issued`，库存释放，并按配置通知兑换人和后台收件人。
- 已批准但尚未自提的订单被取消：是否恢复兑换码由比赛规则决定，默认由管理员确认后恢复或补发新码。
- 已完成自提核销的订单：默认不自动恢复兑换码，进入客服处理流程。
- 任何恢复、补发或作废都必须关联原订单并记录原因。

### 6.4 无账号兑换

平台不维护兑换人账号、密码或用户中心，但可以把兑换码分配给获奖人业务记录，用于发码邮件和后台追踪。兑换码是进入兑换流程的唯一业务凭证；兑换人提交的姓名、手机号等信息只作为本次兑换订单和自提核销信息保存，不用于创建用户。

为降低兑换码泄露和撞库风险，系统应使用不可预测兑换码、输入限流、失败锁定、统一错误提示、后台告警和完整审计。是否增加短信验证码属于未来可选能力，不属于当前账号体系。

## 9. 非功能需求

### 9.1 安全

- 兑换页面和后台使用 HTTPS。
- 只有后台管理员使用账号登录；后台使用 RBAC，高权限操作建议启用二次验证。
- 兑换码采用安全随机生成，服务端校验，数据库中至少保存哈希值；如需找回原码，使用加密存储而不是明文。
- 对兑换码验证、后台登录、导入、导出、SMTP 测试和 Webhook 接口做访问频率限制。
- 防止重复提交、后台越权访问、批量撞码、CSRF、XSS、SQL 注入和敏感信息泄露。
- 生产日志不得记录完整兑换码、完整手机号、证件信息或其他不必要的个人信息。
- 备份、导出和下载链接需要权限控制和过期策略。
- 获奖人名单、兑换码分配表和邮件发送记录属于敏感业务数据，导入、查看、导出和批量重发需要单独权限并记录审计。
- 发码邮件可以包含完整兑换码，但邮件正文、收件人、发送时间和模板版本必须纳入发送日志；Webhook 默认不得包含完整兑换码。

### 9.2 隐私和合规

- 仅收集完成自提和通知所必需的个人信息。MVP 默认必填姓名和手机号；邮箱、证件信息和备注按比赛配置。
- 在收集姓名、手机号、邮箱和证件信息前展示用途说明和隐私提示。
- 获奖人名单中的邮箱和手机号仅用于比赛通知、兑换码关联和必要的自提核验，不用于账号注册或营销，除非另有明确授权。
- 个人信息访问、导出、删除和保留周期应按适用法律、业务合同和公司政策确定。
- 京东商品图片、描述和链接的使用方式应经过业务/法务确认。
- 需要对外发送的数据默认脱敏，并提供字段级开关。

### 9.3 稳定性和一致性

- 兑换提交必须具备幂等性和并发控制。
- 库存预占、兑换码锁定和订单创建必须保持一致，不能出现“有码无单”或“有单无码”。
- Webhook 和 SMTP 邮件发送采用异步队列，不应阻塞兑换人提交。
- 外部链接抓取失败不影响奖品人工录入和其他比赛使用。
- 关键业务数据应有备份、恢复和故障告警方案。

### 9.4 性能和体验目标

- 常规兑换页面和后台页面在正常网络下首屏响应目标为 P95 小于 2 秒；外部抓取、SMTP 和 Webhook 通知不计入同步请求时间。
- 兑换码校验应在 1 秒内返回，超时由系统记录并告警。
- 兑换页面优先适配手机端。
- 错误提示应说明兑换人下一步能做什么，但不能泄露安全敏感信息。
- 时间统一使用配置时区展示，服务端保存带时区的时间戳。

## 10. 验收标准

### 10.1 比赛和奖品

- 管理员可以创建比赛，配置时间、自提规则和奖品范围。
- 管理员可以在同一比赛中创建多个不同额度的兑换码批次，并分别生成指定数量的兑换码。
- 管理员可以导入获奖人名单，按行指定兑换码批次或额度，并在确认前看到完整校验结果。
- 导入确认后，系统可以为获奖人分配正确额度的兑换码，并自动发送兑换码邮件。
- 管理员可以手工创建奖品，上传图片并设置名称、描述和兑换额度。
- 输入一个可访问的京东商品链接后，系统可以展示抓取预览；管理员确认后才能保存。
- 抓取失败时能够手工录入，不会产生半成品奖品或阻塞后台。
- 下架奖品不能产生新订单，历史订单仍能查看原始快照。

### 10.2 兑换码和兑换

- 批量生成的兑换码全局唯一、不可预测，并能关联到正确的比赛、兑换码批次和额度。
- 同一比赛中的 300 元码、500 元码等不同额度兑换码，均能正确展示各自可兑换的奖品范围。
- 兑换流程不要求注册、登录或创建用户账号。
- 未发布比赛、过期、作废、已使用或被锁定的兑换码不能重复兑换。
- 兑换人只能看到额度范围内可兑换的奖品。
- 并发或重复点击提交不能生成多个有效订单。
- 订单中保留奖品、额度、规格、姓名、手机号、自提地点和自提规则快照；不包含收货地址或物流信息。
- 姓名和手机号为必填，手机号格式校验有效；兑换人可以按配置填写邮箱、证件信息和备注。
- 缺少邮箱、邮箱格式错误、批次不存在、额度不匹配或批次可用码不足时，系统不得分配错误兑换码或发送邮件，并提供逐行错误报告。
- 重复导入同一外部获奖人 ID不得重复生成兑换码或重复发邮件；管理员明确重发时才允许再次发送。
- 邮件发送失败后，管理员可以只重发失败邮件，也可以批量重发；重发结果和模板版本可追踪。
- 管理员可以将订单审核为“待备货”，再完成“待自提”和“已自提核销”。
- 订单被拒绝时，系统按配置释放库存并恢复或补发兑换资格。

### 10.3 后台和通知

- 管理员可以查询、筛选、导出订单和兑换码。
- 管理员可以配置 SMTP 邮件服务器、收件人、发件人和模板，并能发送测试邮件。
- 管理员可以创建、编辑、预览、测试、发布和版本化兑换码通知邮件模板。
- 模板支持主题、纯文本和 HTML 内容，并提供获奖人姓名、兑换码、额度、有效期和兑换入口等变量。
- 管理员可以查看获奖人导入结果、兑换码分配关系、邮件发送状态、失败原因、重试次数和模板版本。
- 订单状态变更、兑换码批次操作等事件，正确触发已启用的 SMTP 邮件和 Webhook。
- Webhook 和 SMTP 发送记录包含发送状态、失败原因、重试次数和最后一次尝试时间。
- Webhook 失败会记录错误并按策略重试；管理员可以查看和手工重试。
- 所有关键操作都能在审计日志中查到操作人、时间、对象和原因。

## 12. 风险与应对措施

| 风险 | 影响 | 应对 |
|---|---|---|
| 外部商品页面不可访问或结构变化 | 无法自动导入或字段错误 | 抓取仅做辅助；预览确认；保留人工录入；记录抓取版本。 |
| 自有库存录入或盘点不准确 | 兑换后无法出库或出现超卖 | 平台维护总量、预占量、已出库量和库存流水；提交时锁定库存；设置盘点和异常调整流程。 |
| 兑换码泄露或转让 | 非预期人员兑换 | 不可预测码、限流、统一错误提示、现场手机号核验、审计和作废/补发机制。 |
| 获奖人导入错误或额度分配错误 | 获奖人收到错误额度或错误兑换码 | 导入模板、逐行校验、批次容量校验、确认前预览、分配关系审计和重复导入幂等。 |
| 邮箱无效、退信或邮件进入垃圾箱 | 获奖人未收到兑换码 | 邮箱格式校验、发送状态、退信/失败记录、重试、批量重发和后台导出兜底。 |
| 邮件模板变量或内容配置错误 | 邮件内容缺失或发错兑换码 | 模板变量校验、示例预览、测试邮件、版本发布和模板快照。 |
| 并发兑换导致超库存或重复订单 | 财务和履约错误 | 事务、锁定、幂等键、库存预占和状态机。 |
| 自提个人信息泄露 | 隐私和合规风险 | 只收集姓名、手机号等必要字段；字段级权限、加密、脱敏、留存期限和访问审计。 |
| 通知服务失败 | 业务无法及时获知订单 | 异步发送、重试、失败告警、后台补发。 |
| 规则修改影响已导出或已分发兑换码 | 产生争议 | 规则版本化、批次快照、订单快照、变更审批和审计。 |
| 京东资料抓取越界或页面规则变化 | 抓取失败、资料不完整或产生合规风险 | 只抓取允许访问的公开资料；预览确认；提供人工录入；必要时使用已授权的数据接口。 |

## 13. 需要业务确认的问题

以下问题会直接影响产品和技术方案，建议在立项前确认：

1. 已确认不需要采购；自提地点是固定一个，还是同一比赛支持多个自提地点？
2. 一个兑换码是“一次兑换一个奖品”，还是“可分多次消费的余额”？第一版建议一次兑换一个奖品。
3. 奖品价格低于兑换码额度时，剩余额度如何处理？建议不返现、不结转。
4. 奖品价格高于兑换码额度时，是否允许补差价？第一版建议不允许。
5. 获奖人名单包含哪些字段？默认建议包含外部获奖人 ID、姓名、邮箱、手机号、兑换码批次标识或兑换额度。
6. 每名获奖人默认一个兑换码是否确认？是否存在一个获奖人多个兑换码的场景？
7. 获奖人导入后是否立即自动发码，还是需要管理员二次确认后发送？推荐“导入预览—确认分配—自动发送”。
8. 自动发码邮件是否必须发送完整兑换码？当前需求建议发送完整兑换码，并通过模板权限、日志和重发审计控制风险。
9. 自提申请除姓名和手机号外，是否必须收集邮箱、证件类型/号码或其他字段？默认建议只有姓名和手机号必填。
10. 订单是否需要管理员审核？第一版建议需要，以便确认库存和备货。
11. 自提时核验哪些信息：订单号、兑换码、手机号、姓名，是否需要二维码或短核销码？
12. 已确认平台兑换额度不从京东价格自动计算；是否需要额外展示京东参考价，以及参考价的更新时间？
13. 自有库存以什么形式提供：按 SKU/规格提供数量，还是还需要批次、序列号和有效期？库存是否通过表格批量导入？
14. 京东链接抓取是否有已授权的接口或数据来源？如果没有，应确认抓取范围和合规边界。
15. SMTP 是否使用公司现有邮件服务器？需要 TLS、STARTTLS、应用专用密码还是其他认证方式？
16. 是否需要每个比赛使用独立的邮件模板，还是使用全局模板加比赛级覆盖？推荐两级模板。
17. 通知接收方是谁：业务运营邮箱、比赛主办方、外部业务系统，还是获奖人邮箱？
18. Webhook 需要发送哪些字段，是否允许发送手机号等敏感信息？
19. 预计同时进行的比赛数量、获奖人规模、兑换码规模、订单峰值和数据保留期限是多少？
20. 是否需要对接现有比赛系统、CRM、邮件系统或企业内部身份系统？

## 14. 推荐的首期实现顺序

1. 先确定获奖人导入字段、每人兑换码数量、额度分配规则、自提点配置和通知字段。
2. 完成比赛、获奖人、奖品、兑换码批次、兑换码和库存的数据模型与后台基础管理。
3. 完成获奖人导入预览、去重、额度匹配、兑换码分配和自动发码队列。
4. 完成兑换码验证、奖品筛选、订单创建和并发/幂等控制。
5. 完成订单审核、库存预占、自提备货、现场核销和报表导出。
6. 接入 SMTP 邮件和 Webhook，并补齐邮件模板编辑、版本、测试、签名、重试、日志和批量重发。
7. 最后接入京东链接导入，先做“抓取预览 + 人工确认”，后续再评估是否需要批量刷新商品资料。
8. 用一场小规模比赛进行灰度测试，验证不同额度兑换码、批量导入、自动发码、自提核销、异常恢复、通知和隐私处理后再扩大规模。

## 15. 成功指标建议

- 兑换码有效兑换成功率。
- 从输入兑换码到提交订单的平均耗时。
- 重复订单、无效码、库存不足和提交失败率。
- 订单从提交到审核、备货、自提核销和完成的平均时间。
- 邮件/Webhook 成功送达率和平均重试次数。
- 获奖人导入成功率、兑换码正确分配率和自动发码成功率。
- 兑换码邮件退信率、重发率和从导入确认到发码的平均时间。
- 邮件模板因变量错误导致的发送失败数。
- 需要人工客服介入的订单比例。
- 奖品抓取后需要人工修正的字段比例。

## 16. 推荐技术栈与架构评估

### 16.1 推荐结论

推荐采用：

> **Vue 3 + TypeScript + Vite + shadcn-vue/Tailwind CSS 前端 + Python FastAPI API + SQLAlchemy 2 + MySQL/InnoDB + SQL 任务表 + SMTP/Webhook。**

开发、测试和生产环境统一使用 MySQL/InnoDB；MySQL 是所有环境的唯一数据库。由于服务器已有 MySQL，这样不增加新的数据库基础设施，同时适合获奖人批量导入、自动发码、邮件重试、Webhook 重试和多人后台操作。

### 16.2 组件选择

| 层次 | 推荐方案 | 选择理由 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | 适合构建兑换页面和后台管理界面；使用 Composition API、Single-File Components。 |
| 前端组件 | shadcn-vue + Tailwind CSS | 使用可复制、可直接维护的 Vue 组件源码，覆盖表格、表单、上传、分页、弹窗、确认框和批量操作；保持后台视觉和交互一致。 |
| 前端状态 | Pinia 仅用于登录态、比赛配置和跨页面状态 | 页面局部状态优先使用 Vue Composition API，避免不必要的全局状态。 |
| 后端 API | Python + FastAPI + Pydantic | API、参数校验、OpenAPI 文档和权限依赖清晰；与 Vue 前后端分离匹配。 |
| ORM/迁移 | SQLAlchemy 2 + Alembic | 管理 MySQL 模型、事务和迁移；将数据库访问集中在 service/repository 层。 |
| 管理后台 | Vue 自定义后台页面 | 获奖人导入预览、兑换码分配、邮件模板编辑、批量操作等流程需要定制交互，不依赖通用后台生成器。 |
| 管理员认证 | FastAPI API + HttpOnly Cookie 会话 + MySQL 管理员表 | 只给后台管理员建立账号；兑换人和获奖人不建立登录账号。 |
| 数据库 | MySQL 8.x + InnoDB（开发、测试、生产统一） | 服务器已有 MySQL；事务、行锁和多连接能力适合兑换码、库存预占和后台并发操作。开发和测试使用独立数据库或 schema，避免污染业务数据。 |
| 异步任务 | MySQL 任务表 + 独立轻量 worker | 不引入 Redis、Celery、RabbitMQ；邮件和 Webhook 任务持久化、可重试、可审计。 |
| 邮件 | Python SMTP 客户端 | 复用 SMTP 配置，支持测试邮件、模板渲染和发送结果记录。 |
| Webhook | Python HTTP 客户端 + 数据库任务表 | 支持 HTTPS、签名、超时、指数退避、幂等键和手工重试。 |
| 京东资料抓取 | HTTP 客户端 + HTML 解析器；必要时再加浏览器渲染 | 第一版优先抓公开页面并提供人工回退，不为抓取功能引入常驻浏览器服务。 |
| 图片/导入文件 | MySQL BLOB/LONGBLOB + SQL 元数据表 | 贯彻“全部业务数据放 SQL”；保存商品图片、导入原件和错误明细，设置单文件大小上限并记录 MIME、哈希和来源。 |
| 部署 | 单台 Linux 服务器 + Nginx/Caddy + Uvicorn + worker | 组件少、容易备份和排错；MySQL 使用现有实例，Vue 构建产物由 Nginx/Caddy 提供。 |
| 测试 | pytest + FastAPI TestClient + MySQL 测试数据库 | 覆盖导入、分配、兑换、库存预占、自提核销、模板渲染和通知重试，并使用真实 MySQL 语义验证事务与锁。 |

### 16.3 “全部放 SQL”的持久化边界

本项目按“所有运行时业务数据统一进入 SQL”设计，MySQL 是线上唯一事实来源，不引入 Redis、NoSQL、文件型 JSON/YAML 配置或本地 `media/` 目录来保存业务状态。至少以下内容必须落 MySQL：

- 比赛、兑换规则、额度批次、获奖人、导入文件原件和逐行导入错误。
- 奖品资料、京东抓取快照、商品图片二进制、规格、参考价格和自有库存流水。
- 兑换码哈希/加密密文、兑换订单、个人信息快照、自提点和核销记录。
- 邮件模板及版本、SMTP/Webhook 配置、通知任务、发送结果、重试记录和审计日志。

建议使用以下 SQL 结构承载文件型内容：

- `reward_assets`：`reward_id`、`blob_data`、`mime_type`、`original_name`、`size_bytes`、`sha256`、`sort_order`、`created_at`。
- `winner_import_files`：`import_batch_id`、`file_blob`、`mime_type`、`original_name`、`size_bytes`、`sha256`。
- `winner_import_errors`：`import_batch_id`、`row_number`、`raw_row_json`、`error_code`、`error_message`。

前端构建产物、Python 源码和环境变量中的主加密密钥不属于业务数据，可以作为部署文件或密钥配置存在；SMTP 密码、Webhook 签名密钥等业务配置则进入 SQL 加密字段，主加密密钥不得与数据库放在同一处。第一版应限制图片和导入文件大小，并在数据库层做容量监控；只有当附件体量明显增大时，才评估迁移到对象存储。

### 16.4 MySQL/InnoDB 统一数据库方案

所有环境使用 MySQL 8.x + InnoDB。开发环境可连接服务器上的独立开发库，或通过 Docker 启动独立 MySQL 实例；测试环境使用独立测试库，并在每次测试运行前执行迁移或清理测试数据，确保事务、锁和字段行为与线上一致。

兑换提交和库存预占必须在短事务中完成；兑换码、库存行和任务行使用事务与行级锁，事务内不执行 SMTP、Webhook、京东抓取等外部网络请求。[MySQL InnoDB 事务文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-autocommit-commit-rollback.html)、[MySQL InnoDB 锁定读取文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

SQLAlchemy 和 Alembic 统一管理 MySQL 模型、事务和迁移，开发、测试、预发布和生产使用同一套迁移脚本。[SQLAlchemy 2 ORM 文档](https://docs.sqlalchemy.org/en/20/orm/)

### 16.5 轻量任务队列设计

不引入 Redis/Celery，但不能把发送邮件直接绑在用户请求里，也不能只使用进程内的临时后台任务。推荐建立 `notification_jobs` 表：

- `idempotency_key`
- `event_type`
- `winner_id`、`code_id`、`order_id`
- `channel`
- `template_version`
- `status`：pending、processing、sent、failed、dead_letter
- `attempt_count`
- `next_retry_at`
- `last_error`
- `locked_at`、`sent_at`

Web 请求只负责在事务中创建业务数据和任务记录；独立 worker 轮询待处理任务，发送 SMTP/Webhook 后更新结果。worker 重启后可以继续处理未完成任务。发送成功和失败都写入 `NotificationDelivery`，管理员可在后台重试失败任务。

Python SMTP 客户端可以直接连接 SMTP 服务。邮件发送仍应通过持久化任务执行，以保证重试和审计，而不是依赖一次请求生命周期。FastAPI 的官方文档也将小型邮件通知列为可放到后台处理的场景，但这里进一步使用数据库任务表，确保进程重启后任务不会丢失。[FastAPI 后台任务文档](https://fastapi.tiangolo.com/tutorial/background-tasks/)

### 16.6 关键技术约束

- MySQL 表统一使用 InnoDB 和 `utf8mb4`。
- 兑换码、获奖人外部 ID、订单号、任务幂等键和 SKU 建立唯一约束。
- 金额使用整数分，不使用浮点数。
- 兑换提交必须在一个短事务中完成：校验兑换码、锁定兑换码、锁定库存、创建订单和创建通知任务。
- 事务内不执行 SMTP、Webhook、京东抓取或其他外部网络请求。
- 批量导入按小批次提交，避免一个超大事务长时间锁表；每批记录进度和错误行。
- 不启用多个独立 worker 同时处理同一任务，除非任务领取使用 MySQL 行锁或等价的租约机制。
- MySQL 与应用位于同一台服务器或可靠内网；所有上传的业务文件进入 MySQL。
- SMTP 密码、Webhook 签名密钥、Python 应用 secret key 等敏感配置使用环境变量或加密存储，不能写入代码仓库。
- MySQL 数据库按计划备份，并验证 BLOB、导入原件和审计数据可以恢复；`.env` 相关密钥单独安全备份，至少保留一次可恢复备份。

### 16.7 初期不引入的组件

- React、Next.js、Nuxt 等额外前端框架
- Redis、Celery、RabbitMQ、Kafka
- Kubernetes、微服务和独立 API 网关
- Elasticsearch、Prometheus、复杂日志平台
- S3/对象存储（除非图片或附件规模明显增长）
- 京东常驻浏览器集群或自动采购系统

### 16.8 何时从 MySQL 单体升级

只有出现以下情况时再考虑增加 Redis/任务队列、对象存储或拆分服务：

- 需要多台应用服务器同时部署，且通知 worker 需要水平扩展。
- 邮件/Webhook 任务量明显超过单个 worker 的处理能力。
- 图片、附件或导入文件规模不适合继续保存在 MySQL BLOB/LONGBLOB 中。
- 需要多地区部署、读写分离、复杂监控或跨系统高频实时同步。

在当前需求和轻量化目标下，MySQL + 单体应用已经足够，不需要预先为这些未来场景引入基础设施。

---

**结论：** 这个需求适合先做成“比赛 + 获奖人导入 + 多额度兑换码批次 + 自动发码邮件 + 可编辑邮件模板 + 奖品目录 + 自有库存 + 无账号兑换 + 自提核销 + SMTP/Webhook 通知”的闭环系统。当前最需要确认的是获奖人导入字段、每人兑换码数量、邮件发送时机、模板覆盖规则、自提点数量、现场核验方式和 SMTP 配置；用户账号、配送和采购均不属于范围。
